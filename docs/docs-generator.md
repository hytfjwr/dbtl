# Generated docs (`dbtl docs`)

`dbtl docs` writes a static Markdown documentation tree for a dbt project —
one page per node plus an index `README.md` — without starting the TUI, so it
runs anywhere, including CI with no TTY. Commit the output to a repository and
it reads on GitHub or GitLab, Mermaid diagrams included.

```console
$ dbtl docs --out ./dbt-docs                    # auto-detect the data source
$ dbtl docs --manifest target/manifest.json --out docs/lineage
$ dbtl docs --source /path/to/project --out ./dbt-docs --quiet
```

The data source resolves exactly like the TUI's: `--manifest`,
`--source`, `--project`, or auto-detect (`<project>/target/manifest.json` if
present, else the project source). No compile is needed in source mode.

## Output layout

Everything goes under `--out <DIR>`:

```
<DIR>/
  README.md            # index: summary, coverage, lint, orphans, whole-graph diagram
  owners.md            # models grouped by the owner meta value
  tags.md              # tagged models/seeds/snapshots grouped by tag
  groups.md            # models grouped by their dbt group, with access levels
  models/              # one page per model
  sources/             # one page per source
  seeds/  snapshots/  exposures/
  semantic_models/  metrics/  saved_queries/
  other/               # resource types without their own directory
```

File names are sanitized `unique_id`s (a second node mapping to the same name
gets a `_2` suffix). Every link is relative, so the tree works at any URL
depth. Every generated file starts with a `<!-- Generated by dbtl. Do not
edit. -->` marker — the housekeeping flags below rely on it.

The index `README.md` opens with the project's `__overview__` docs block when
the manifest carries one, then a summary enumerating every resource type,
test coverage with a per-layer model table, column-level coverage, a
documentation-coverage section, the lint summary, orphan models, a linked
table of every node, and a whole-project Mermaid diagram (split by layer on
large projects). Its `Includes:` line names the optional inputs that were
actually loaded, and `Selection:`/`Excluding:` lines record a partial run.

Each node page carries a heading bullet list (resource type, materialization,
database/schema, tags, `unique_id`, source file), the description, a columns
table, tests, the SQL (manifest `compiled_code` when present, otherwise raw;
folded into a `<details>` block), lint violations, upstream/downstream links,
a Mermaid lineage figure, and a sorted `meta` table. Empty sections say `No
…` rather than disappearing, so the page shape is stable.

On models and snapshots each declared column also gets an `Upstream` cell of
linked source columns (up to five, then `+K more`) and a `Used by` count of
distinct downstream consumers — the same column-level-lineage engine `dbtl
columns` exposes.

## Lineage diagrams and the Mermaid budget

GitHub refuses to render Mermaid figures past ~50,000 characters or ~500
edges, so every generated figure is bounded to **40,000 characters and 400
edges** — headroom under the real limit.

- **Node pages** draw the lineage `--lineage-depth` hops out (default **2**;
  an integer ≥ 1, or `all` for the node's whole closure — also settable as
  `docs.lineage_depth` in `.dbtl.yml`). If the figure exceeds the budget the
  depth is reduced one hop at a time until it fits, and the page notes the
  reduction. If even depth 1 exceeds it, the figure is replaced by
  `Diagram omitted: N nodes / M edges exceed GitHub's Mermaid limits.` — the
  direct parent/child link lists still render.
- **The index's whole-graph figure** splits by logical layer on large
  projects; a split figure that still exceeds the budget degrades to the
  same omission line plus a table.

Diagrams come from the same Mermaid core the TUI's `m` yank uses, so a page's
figure matches what the app copies for the same view.

## Selecting a subset

`--select <SELECTOR>` / `--exclude <SELECTOR>` (repeatable, the dbt-selector
grammar of `dbtl ls`) generate a partial tree:

```console
$ dbtl docs --out docs/marts --select 'path:marts+'
$ dbtl docs --out docs/no-legacy --exclude 'tag:legacy'
```

Only matching nodes get pages (with no `--select`, every node minus the
exclusions generates). Links into ungenerated pages degrade to plain names,
the index records the selection, and its summary counts stay project-wide.
`state:` selectors compare against `--diff` — the only reason `docs` accepts
`--diff` at all. `--clean` and `--check` can't pair with a partial set.

## Housekeeping: `--check` and `--clean`

- **`--check`** writes nothing. It compares the generated set against `<DIR>`
  on disk, prints one line per difference (a missing page, a changed page, a
  stale marked file), and exits 1 when anything differs. Unlike
  `git diff --exit-code` after regenerating, it also catches stale pages —
  and it needs no checkout step:

  ```console
  $ dbtl docs --out docs/lineage --check
  docs up to date (97 files)
  ```

- **`--clean`** writes the docs, then deletes marked files under `<DIR>`
  that this run did not regenerate — e.g. pages of removed or renamed
  models. Only files carrying the generated marker are ever removed, so
  hand-written `.md` files in the same directory are safe.

## Optional artifacts: catalog and run_results

Generated docs are environment-independent by contract, so two side
artifacts are **strictly opt-in** — never auto-detected:

- `--catalog <path>` (or `docs.catalog: true` in `.dbtl.yml`, which reads
  the conventional sibling `target/catalog.json`) adds a `Warehouse type`
  column and `rows:`/`size:` bullets.
- `--run-results <path>` (or `docs.run_results: true`) adds a `last run:`
  status line per node.

## Determinism and environment independence

Two runs over the same input produce byte-identical files: regeneration is
safe to gate on. To keep committed output identical across machines and CI:

- `~/.config/dbtl/config.yml` is **never** read. The owner grouping reads the
  project `.dbtl.yml`'s `owner_meta_key` (default `owner`) — the page states
  which key it used.
- `target/compiled/` files and mtime staleness are not consulted: the SQL
  section uses the manifest's `compiled_code` or raw SQL only.
- `.dbtl.yml` is the only project file consulted (`docs.catalog`,
  `docs.run_results`, `docs.lineage_depth`, `owner_meta_key`, and the lint
  findings the pages quote).

## In CI

Commit the generated tree and gate pull requests on freshness:

```yaml
- name: Docs are fresh
  run: dbtl docs --out docs/lineage --check
```

or fold the same comparison into `dbtl check` — see the `docs_drift` gate in
[ci.md](ci.md#the-gate-set).
