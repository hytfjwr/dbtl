---
title: dbtl docs
description: Generate a committable Markdown documentation tree for a dbt project, with Mermaid lineage, without starting the TUI.
---

`dbtl docs` writes a static Markdown documentation tree: one page per node plus an index `README.md`. It never starts the TUI, so it runs anywhere, including CI with no TTY. Commit the output to a repository and it reads on GitHub or GitLab, Mermaid diagrams included.

```sh
dbtl docs --out ./dbt-docs                    # auto-detect the data source
dbtl docs --manifest target/manifest.json --out docs/lineage
dbtl docs --source /path/to/project --out ./dbt-docs --quiet
```

The data source resolves like it does for the TUI: `--manifest`, `--source`, `--project`, or auto-detect. Auto-detect uses `<project>/target/manifest.json` if it exists and the project source otherwise. Source mode needs no compile. See [CLI overview](overview.md#choose-the-data-source).

`--quiet` mutes the one-line success summary on stdout. Errors still go to stderr, and a failing `--check` still prints its list of differences.

## Output layout

Everything goes under `--out <DIR>`. `dbtl` creates the directory if it is missing and overwrites existing generated pages.

```text
<DIR>/
  README.md            # index: summary, coverage, lint, orphans, whole-graph diagram
  owners.md            # models grouped by the owner meta value
  tags.md              # tagged models/seeds/snapshots grouped by tag
  groups.md            # models grouped by their dbt group, with access levels
  models/              # one page per model
  sources/             # one page per source
  seeds/  snapshots/  exposures/
  semantic_models/  metrics/  saved_queries/
  other/               # resource types without their own directory
```

File names are sanitized `unique_id`s. A second node that maps to the same name gets a `_2` suffix. Every link is relative, so the tree works at any URL depth. Every generated file starts with a `<!-- Generated by dbtl. Do not edit. -->` marker, which the housekeeping flags rely on.

### The index page

The index `README.md` opens with the project's `__overview__` docs block when the manifest carries one. It then lists:

- a summary that enumerates every resource type, led by a `- scope:` bullet
- test coverage with a per-layer model table
- column-level coverage
- a documentation-coverage section
- the lint summary
- orphan models
- a linked table of every node
- a whole-project Mermaid diagram, split by layer on large projects

Its `Includes:` line names the optional inputs that were loaded. `Selection:` and `Excluding:` lines record a partial run.

The owner, tag, and group index pages sit beside it. Owners come from the `owner_meta_key` in `.dbtl.yml` (default `owner`), and the page states which key it used.

### Node pages

Each node page carries:

- a bullet list with resource type, materialization, database and schema, tags, `unique_id`, and source file — plus the declared governance bullets `language` (only a non-`sql` build), `incremental_strategy`, `deprecation_date`, and `constraints`
- the description
- a columns table
- tests
- the SQL: the manifest's `compiled_code` when present, otherwise the raw SQL, folded into a `<details>` block
- lint violations
- upstream and downstream links
- a Mermaid lineage figure
- a sorted `meta` table

Empty sections say `No …` instead of disappearing, so the page shape stays stable.

On models and snapshots, each declared column also gets an `Upstream` cell with linked source columns (up to five, then `+K more`) and a `Used by` count of distinct downstream consumers. Both come from the same column-level lineage engine as [`dbtl columns`](columns.md).

## Lineage diagrams and the Mermaid budget

GitHub refuses to render Mermaid figures past about 50,000 characters or 500 edges. Every generated figure is bounded to 40,000 characters and 400 edges, which leaves headroom under the real limit.

- **Node pages** draw the lineage `--lineage-depth` hops out. The default is 2. Pass an integer of 1 or more, or `all` for the node's whole closure. You can also set it as `docs.lineage_depth` in `.dbtl.yml`.
- **When a figure exceeds the budget**, `dbtl` reduces the depth one hop at a time until it fits, and the page notes the reduction. If even depth 1 exceeds it, the figure becomes `Diagram omitted: N nodes / M edges exceed GitHub's Mermaid limits.` The direct parent and child link lists still render.
- **The index's whole-graph figure** splits by logical layer on large projects. A split figure that still exceeds the budget degrades to the same omission line plus a table.

Diagrams come from the same Mermaid core that the TUI's `m` yank uses, so a page's figure matches what the app copies for the same view.

## Select a subset

`--select <SELECTOR>` and `--exclude <SELECTOR>` generate a partial tree. Both are repeatable and use the [selector grammar](selectors.md).

```sh
dbtl docs --out docs/marts --select 'path:marts+'
dbtl docs --out docs/no-legacy --exclude 'tag:legacy'
```

Only matching nodes get pages. With no `--select`, every node minus the exclusions generates. Links into ungenerated pages become plain names. The index records the selection, and its summary counts stay project-wide.

`state:` selectors compare against `--diff`. That is the only reason `docs` accepts `--diff`. `--clean` and `--check` cannot be combined with a partial set.

## Housekeeping: check and clean

`--check` writes nothing. It compares the generated set against `<DIR>` on disk, prints one line per difference (a missing page, a changed page, or a stale marked file), and exits 1 when anything differs. Unlike running `git diff --exit-code` after regenerating, it also catches stale pages, and it needs no checkout step.

```sh
dbtl docs --out docs/lineage --check
```

```text
docs up to date (97 files)
```

`--clean` writes the docs, then deletes marked files under `<DIR>` that this run did not regenerate, such as pages of removed or renamed models. Only files that carry the generated marker are removed, so hand-written `.md` files in the same directory are safe.

```sh
dbtl docs --out ./dbt-docs --clean
```

## Optional artifacts: catalog and run_results

Generated docs are environment-independent by contract. Two side artifacts are opt-in and never auto-detected:

- `--catalog <path>`, or `docs.catalog: true` in `.dbtl.yml`, adds a `Warehouse type` column and `rows:` and `size:` bullets. The `.dbtl.yml` option reads the conventional sibling `target/catalog.json`.
- `--run-results <path>`, or `docs.run_results: true`, adds a `last run:` status line per node.

## Determinism and environment independence

Two runs over the same input produce byte-identical files, so you can gate on regeneration. To keep committed output identical across machines and CI:

- `~/.config/dbtl/config.yml` is never read. The owner grouping reads `owner_meta_key` from the project's `.dbtl.yml`.
- `target/compiled/` files and modification-time staleness are not consulted. The SQL section uses the manifest's `compiled_code` or the raw SQL.
- `.dbtl.yml` is the only project file consulted. It supplies `docs.catalog`, `docs.run_results`, `docs.lineage_depth`, `owner_meta_key`, and the lint findings the pages quote.

## In CI

Commit the generated tree and gate pull requests on freshness:

```yaml
- name: Docs are fresh
  run: dbtl docs --out docs/lineage --check
```

You can also fold the same comparison into `dbtl check` with the `docs_drift` gate. See [Check and impact](check-and-impact.md#the-gate-set) and [Other CI systems](../ci/other-ci.md#docs-drift).
